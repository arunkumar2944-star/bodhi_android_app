# Recover the running work session after eligibility API failures

An eligibility GET previously called stopSelf() on any exception. A Wi-Fi-to-mobile handover, timeout, server 5xx, missing deployment or malformed response could permanently stop the running foreground service until another app opening. This is a verified code failure path, not proof of the cause of any particular missed break.

The running service now preserves its work-session runtime and stays foreground while awaiting fresh daily eligibility. It makes no GPS requests or attendance decisions while waiting, clears the displayed sensor snapshot, and shows “Verification pending — reconnecting to CRM; GPS paused”. It retries after 30 seconds, then 60, then at most 120 seconds. A newly available default network can wake the retry earlier. One retry loop owns this behavior; there is no new scheduled service start or morning automation.

Each failure writes an API_RETRY diagnostic to Room with a safe HTTP status/exception type, attempt and retry delay, and also logs ATTENDANCE_MONITOR. No token, response body, emergency reason or URL is logged. API_RECOVERED records recovery and schedules the existing network-only saved-record upload. Normal event sync/evidence capture resumes only after current-day eligibility succeeds. Pending Room events keep their original UUIDs/timestamps; network recovery does not fabricate a break, infer absence from disconnected Wi-Fi alone, or backdate an event over an unobserved interval.

Explicit HTTP 401/403 denies access and stops monitoring with a persisted API_BLOCKED diagnostic. A fresh PAUSED decision (holiday, leave, emergency absence, checked out, etc.) or changed server date stops monitoring with POLICY_PAUSED. Local checkout/logout still stops the service. These are distinct from retryable transport/server failures. Missing/invalid local session responses remain sensor-paused while the existing token provider is retried; this does not grant attendance permission.

Manual morning opening remains required. The foreground service is START_NOT_STICKY: this change does not silently restart an OS-killed/force-stopped service. Startup eligibility/reconciliation must still succeed while the app is visible before starting a session; the recovery loop protects a service whose visible startup was already authorized. No Android permission, Room schema or backend migration changes are required.

AutomaticAttendanceEvaluator still requires fresh accurate office evidence and continuity; a long outage can invalidate old outside observations and require new observations/grace. API recovery is not a promise of offline GPS capture or recovery of an exact departure time that was never observed. Separate configuration API errors remain conservative and do not authorize events; the normal loop can retry them.

Validation: added JVM tests for HTTP retry/access-denial classification and bounded backoff. Gradle/JVM execution and full APK compilation are blocked in this workspace by unavailable network access to the configured Gradle distribution. Static diff/whitespace checks pass. On a real device, start an eligible session visibly, switch office Wi-Fi to mobile data, interrupt/recover the eligibility endpoint, inspect API_RETRY/API_RECOVERED in Room/CRM, verify no GPS while waiting, and verify normal BREAK_START after reliable outside evidence plus configured grace. Also test 401/403, PAUSED response, checkout during a retry, manual next-day opening, and OS process termination.
